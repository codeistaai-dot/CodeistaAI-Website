DEFAULT TECHNOLOGY FOR NEW WEBSITES

All new production websites must be built using:

- Next.js App Router
- TypeScript
- A currently supported and security-patched Next.js LTS version
- Server Components by default
- Client Components only where state, events, forms, menus, modals, animations, or browser APIs require them

Do not start a new production website with plain React/Vite unless my manager explicitly requests it.

Standalone HTML may be created first only when I ask for a UI prototype. The approved prototype should later be migrated faithfully into Next.js.

TWO-REPOSITORY CLIENT STRUCTURE

The normal client structure is:

1. Landing-page repository — create this first.
2. Lead-dashboard repository — create later, only after backend APIs and dashboard requirements are available.

Do not put dashboard pages, authentication, admin screens, database logic, backend business logic, or lead-management features inside the landing-page repository.

The landing-page form should be prepared to connect to backend APIs later through a clean, isolated integration layer.

UTM ATTRIBUTION DURING LANDING-PAGE DEVELOPMENT

Prepare UTM attribution during the initial landing-page development whenever lead-source tracking will be required. Follow UTM_TRACKING_CONTEXT_AND_INSTRUCTIONS.txt for the complete workflow.

- Add a client-specific, isolated tracking utility and lightweight capture component while building the form.
- Keep the root Next.js layout as a Server Component.
- Capture only explicitly approved UTM and click-ID parameters.
- Sanitize and preserve approved attribution in a client-specific sessionStorage key so it survives navigation to a clean URL.
- Never store form PII, credentials, tokens, database URLs, or unknown query parameters in browser storage.
- If the backend API contract is available, submit only its approved optional tracking fields and clear attribution only after verified API success.
- If the backend contract is not available, do not invent an endpoint, payload fields, collection, or relationship. Keep attribution capture isolated and document what must be confirmed with the backend developer.
- A lead without UTM parameters must still be accepted once the real API is connected.
- Treat every client's allowlist, storage key, API contract, database, and campaign model as separate.

MOBILE ALIGNMENT REQUIREMENT

Every website must be properly centred and balanced on mobile widths from 375px to 414px.

Check:

- Headings
- Paragraphs
- Eyebrow labels
- Buttons and CTA groups
- Cards and grids
- Images
- Icons with text
- Chips and tabs
- Forms and validation messages
- Navigation
- Modals
- Footer content

Recurring mobile traps:

1. text-align: center does not centre flex children. Use justify-content: center.
2. Centred max-width text boxes also need automatic left and right margins.
3. Inline styles override stylesheet media queries.
4. Remove or convert inline desktop grid styles that block responsive layouts.
5. Mobile menus must be opaque, cover the content underneath, and use the correct stacking order.
6. Lock background scrolling when a full-screen menu or modal is open.
7. Tables must scroll inside their own container.
8. Do not use overflow-x: hidden as the only fix. Identify the element causing overflow.
9. Verify document.documentElement.scrollWidth <= document.documentElement.clientWidth at 375px, 390px, and 414px.

Forms and data tables may remain internally left-aligned where that improves readability.

FORM VALIDATION REQUIREMENTS

Form validation is always high priority.

Implement appropriate client-side and server-side validation:

- Mark required fields clearly.
- Trim whitespace.
- Reject spaces-only values.
- Use sensible field-length limits.
- Validate names, email addresses, phone numbers, numeric values, and required selections.
- Use the correct phone rules for the intended country.
- Show short, specific errors below the relevant field.
- Do not communicate errors using colour alone.
- Use aria-invalid and aria-describedby.
- Focus the first invalid field after a failed submission.
- Clear errors when fields become valid.
- Preserve values after failed validation.
- Prevent duplicate submissions.
- Never log personal information.
- Show success only after a real API confirms success.

If no backend exists yet:

- Do not invent an endpoint.
- Do not invent a payload or API response.
- Do not fake a production submission.
- Clearly label local success as a UI demo.
- Keep API integration isolated so it can be connected later.
- Document what is required from the backend developer.

Keep webhook URLs, API keys, and secrets server-only. Never expose them through NEXT_PUBLIC_.

For public lead forms, use basic spam protection such as a honeypot and keep future rate limiting possible.

ANIMATIONS

ENVIRONMENT VARIABLES

Environment variables that work locally do not automatically exist on Vercel.

- Keep placeholders in .env.example.
- Never commit secrets.
- Ensure secret .env files are ignored by Git.
- Configure variables separately for Vercel Preview and Production.
- Test the real integration on the Preview URL.
- Confirm Production variables before updating main.

GIT AND VERCEL WORKFLOW

Merging or updating main automatically triggers Vercel Production Deployment.

Normal workflow:

1. Collect requirements and assets.
2. Work on a preview/staging branch.
3. Use clear local commits.
4. I push the preview branch manually.
5. Share and test the Vercel Preview URL.
6. Obtain manager approval.
7. Confirm Production environment variables.
8. Update main only after approval.
9. Vercel automatically deploys Production.
10. Verify the production URL and real form submission.

If Vim opens during a merge or pull, type :wq and press Enter to accept the default message and close it.

Do not recommend destructive Git commands casually. Before replacing main with another branch, explain whether the action is a merge, fast-forward, or history replacement. If a non-fast-forward error occurs, do not suggest force until the desired exact branch state is confirmed. Prefer --force-with-lease over --force when replacement is explicitly authorized.

Do NOT run git push — commit locally only, I'll push myself.

DOMAIN AND DNS WORKFLOW

When access is available:

1. Add the domain in Vercel under Settings → Domains.
2. Copy the exact A/CNAME records Vercel provides.
3. Add those records at the registrar or Cloudflare, depending on where DNS is managed.
4. Wait for Valid Configuration in Vercel.
5. Verify the custom domain loads the Production deployment.

A DNS server maps a domain name to the destination server. A custom domain points to the Production branch, not preview deployments. Preview URLs remain on Vercel preview domains.
